## 1. Назначение

Прошивка управляет механическим нагрузочным стендом: шаговый двигатель через механизм зажимает объект между плитами, тензодатчик HX711 измеряет силу
сжатия в килограммах, магнитный энкодер AS5600 отслеживает угол вала. Задача стенда - довести силу сжатия до заданного целевого окна и удерживать её
неизменной, чтобы над зажатым объектом можно было вести измерения.

Управление построено на явном конечном автомате. Стенд можно вести двумя независимыми путями:

- **физической кнопкой** - для автономной работы без сети;
- **по сети** - командами REST и WebSocket с внешнего дашборда, с одновременной трансляцией телеметрии.

Оба пути ведут один и тот же автомат через единую точку применения команд, поэтому сеть и кнопка не конфликтуют и работают совместно.

Ключевые возможности:

- поиск целевой нагрузки с автоматическим центрированием в заданном окне;
- жёсткое удержание позиции после парковки без подстройки (обоснование - в разделе 7);
- корректный возврат в домашнюю позицию с обходом механической стенки;
- калибровка нуля тензодатчика на лету без перепрошивки;
- задание целевой нагрузки и диапазона в рантайме с сохранением в энергонезависимую память;
- диагностика пропуска шагов по энкодеру;
- телеметрия и удалённое управление по сети.

## 2. Аппаратная конфигурация и распиновка

Плата: `ESP32-S3 DevKit` (окружение сборки `esp32-s3-devkitc-1`). Все управляющие сигналы рассчитаны на логику 3.3 В со стороны микроконтроллера.

### Шаговый драйвер (интерфейс PUL/DIR)

Драйвер подключается по дифференциальным линиям шага, направления и разрешения. Схема «общий плюс»: линии `+` постоянно в логической
единице, сигнал подаётся на линии `-` (активный уровень - ноль). Прежнюю схему (линии `-` на земле, активны `+`) возвращает
`DRIVER_PLUS_PINS_HIGH = false` в `Config.h`.

| Сигнал | GPIO |
|---|---|
| `PUL+` (шаг) | 4 |
| `PUL-` | 5 |
| `DIR+` (направление) | 6 |
| `DIR-` | 7 |
| `EN+` (разрешение) | 10 |
| `EN-` | 9 |

Обе линии `EN` держатся в единице: ток через вход разрешения не идёт, драйвер постоянно включён.

Параметры шага: микрошаг `4`, `800` импульсов на оборот, отсюда `0.45°` на один шаг мотора.

### Энкодер AS5600 (I2C)

| Сигнал | GPIO |
|---|---|
| `SCL` | 17 |
| `SDA` | 18 |

Энкодер даёт абсолютный угол в пределах одного оборота (12 бит, 4096 отсчётов на оборот).

### Тензодатчик через HX711

| Сигнал | GPIO |
|---|---|
| `SCK` (такт от контроллера) | 15 |
| `DOUT` (данные от датчика) | 16 |

HX711 - это не I2C. У него отдельная линия такта `SCK` и линия данных `DOUT`.

### Кнопка

| Сигнал | GPIO |
|---|---|
| Кнопка | 19 |

Кнопка подключена в режиме `INPUT_PULLUP`: нажатие замыкает вход на землю (переход в `LOW`). Дребезг гасится программно.

## 3. Структура проекта

Прошивка разбита на модули с узкой ответственностью. Драйверы периферии не знают о конечном автомате; координация собрана в главном файле скетча.

| Файл | Роль |
|---|---|
| `src/esp32s3_load_stand.ino` | координация: конечный автомат, задачи FreeRTOS, разделяемое состояние, логика поиска/удержания/возврата, обработчик сетевых команд, Serial-диагностика |
| `src/Config.h` | все пины и настраиваемые параметры (пороги, тайминги, калибровки, сеть) |
| `src/SystemState.h` | перечисление состояний автомата и `toString()` |
| `src/ButtonInput.{h,cpp}` | опрос кнопки с программным антидребезгом |
| `src/EncoderTracker.{h,cpp}` | AS5600: чтение угла, многооборотный учёт, логический ноль |
| `src/LoadCellManager.{h,cpp}` | HX711: чтение, медианная фильтрация, перевод в килограммы |
| `src/StepperMotor.{h,cpp}` | генерация импульсов шага, направление, учёт ожидаемой позиции |
| `src/NetCommand.h` | разбор текстовых команд (`seek`/`home`/`stop`/`tare`) |
| `src/NetworkManager.{h,cpp}` | WiFi, mDNS, HTTP-сервер, WebSocket, очереди команд и событий |
| `src/Telemetry.{h,cpp}` | сборка JSON телеметрии и событий |
| `src/ConfigStore.{h,cpp}` | хранение конфигурации в энергонезависимой памяти (NVS) |

Внешние библиотеки (ставятся автоматически): `robtillaart/AS5600`, `bogde/HX711`, `ESP32Async/AsyncTCP`, `ESP32Async/ESPAsyncWebServer`. `Wire` - из ядра Arduino.

### Разделение ответственности

- **Драйверы периферии** (`ButtonInput`, `EncoderTracker`, `LoadCellManager`, `StepperMotor`) - объекты без знания о состоянии системы. Только читают датчики и выдают сигналы.
- **Координация** (`esp32s3_load_stand.ino`) - владеет автоматом, разделяемым состоянием и всей управляющей логикой.
- **Сеть** (`NetworkManager`, `NetCommand`, `Telemetry`) - транспорт: принимает команды в очередь, отдаёт телеметрию. Автомат напрямую не трогает, чтобы исключить межъядерные гонки (см. раздел 12).
- **Конфигурация** (`Config.h`, `ConfigStore`) - статические умолчания и их энергонезависимые переопределения.

## 4. Многозадачность и распределение по ядрам

Прошивка использует две закреплённые за ядрами задачи FreeRTOS плюс основной цикл Arduino. Такое разделение изолирует блокирующую механику от
лёгкой периодики и отдаёт всю работу с мотором и энкодером одному владельцу.

| Задача | Ядро | Приоритет | Стек | Период | Ответственность |
|---|---|---|---|---|---|
| `loadTask` | 0 | 1 | 4096 | 20 мс | чтение HX711, фильтрация, публикация нагрузки в разделяемое состояние |
| `motorTask` | 1 | 2 | 6144 | 2 мс | энкодер AS5600, шаги мотора, homing, поиск/удержание нагрузки, возврат домой |
| `loop()` | - | - | - | ~5 мс | опрос кнопки, применение сетевых команд, Serial-диагностика, обслуживание сети |

### Почему именно так

- **`motorTask` - единственный владелец мотора и энкодера.** Всё, что двигает вал или читает угол по I2C, происходит в этой задаче. Это исключает одновременный доступ к AS5600 и драйверу с двух ядер. Даже стартовый homing и восстановление из аварии выполняются здесь, а не в `loop()` или `setup()`: другие контексты лишь выставляют флаг-намерение, а саму механику крутит `motorTask`.
- **`loadTask` - единственный, кто пишет поля нагрузки.** Чтение HX711 медленное (десятки миллисекунд), поэтому оно вынесено в отдельную задачу на другое ядро и не тормозит ни мотор, ни сеть.
- **`loop()` остаётся лёгким.** Он не содержит блокирующей механики. Благодаря этому кнопка, диагностика и сеть отзывчивы даже пока `motorTask` выполняет длительный homing или поиск нагрузки.

### Ключевое решение: неблокирующий старт

`setup()` не запускает homing напрямую. Он лишь выставляет флаг `gBootHomeRequested` и сразу возвращается. Возврат в логический ноль выполняет
`motorTask` на первой же итерации. Благодаря этому:

- диагностический `loop()` и сетевой стек поднимаются немедленно;
- телеметрия, WiFi, кнопка и удалённые команды живы уже во время homing;
- если homing застрянет (упор в стенку, неверное направление), оператор это видит и может вмешаться, а не наблюдает немую систему до сброса по питанию.

## 5. Разделяемое состояние

Данные, к которым обращаются несколько ядер, собраны в трёх глобальных структурах. У каждой - **свой независимый spinlock** (`portMUX`), и они никогда
не вкладываются друг в друга. Разделение блокировок сделано намеренно: горячая критическая секция телеметрии/энкодера не должна конкурировать с редкими
записями конфигурации или нуля.

| Структура | Блокировка | Содержимое | Кто пишет |
|---|---|---|---|
| `gShared` | `gShared.mux` | состояние автомата, нагрузка (кг и сырые отсчёты), углы энкодера, флаги готовности и аварии, событие кнопки | `loadTask`, `motorTask`, `loop()` |
| `gConfig` | `gConfig.mux` | целевая нагрузка и границы окна (`targetKg`, `minKg`, `maxKg`) | сетевой обработчик `/v1/config`, старт |
| `gOffset` | `gOffset.mux` | оперативный ноль HX711 (сырые отсчёты) | путь перетарирования, старт |

### Правила доступа

- Все поля `volatile`, доступ только через геттеры/сеттеры, берущие соответствующий spinlock.
- Для согласованного чтения группы полей используется единый снимок под одной критической секцией. Так, `getTelemetrySnapshot()` копирует все поля `gShared` за один заход, затем отдельно берёт `gConfig` и `gOffset`. Это исключает «разорванное» чтение, когда часть полей относится к одному моменту, а часть - к другому.
- `gOffset` вынесен в отдельную блокировку, потому что читается в горячих путях **на обоих ядрах**: `loadTask` применяет его к каждому чтению датчика, а `motorTask` использует его в переводе сырых отсчётов в килограммы.

### Флаги-намерения

Отдельные `volatile`-флаги передают намерения между контекстами без прямого вызова механики с чужого ядра:

- `gBootHomeRequested` - просьба `setup()` к `motorTask` выполнить стартовый homing;
- `gRehomeRequested` + `gRehomePolicy` - просьба (от кнопки или сети) восстановиться из аварии или выполнить homing по требованию;
- `gHomeReferenceSteps` - опорная позиция шагов, от которой отсчитывается предел хода при возврате домой.

Такой приём («команда лишь выставляет флаг, механику крутит владелец мотора») - основной способ избежать межъядерных гонок по I2C и мотору.

## 6. Конечный автомат

Семь состояний:

| Состояние | Смысл |
|---|---|
| `BOOT` | базовый старт до инициализации периферии |
| `HOMING` | доезд к домашнему углу энкодера и захват логического нуля |
| `IDLE` | ожидание команды; мотор стоит |
| `SEEK_LOAD` | поиск целевой нагрузки: пошаговое центрирование в окне |
| `HOLD_LOAD` | жёсткое удержание позиции после парковки |
| `RETURN_HOME` | возврат к логическому нулю |
| `ERROR` | авария по энкодеру или застреванию возврата |

Каждая смена состояния проходит через единственную функцию `setState()`, которая заодно рассылает WebSocket-событие о переходе. Поэтому дашборд
получает уведомление о любом переходе мгновенно, не дожидаясь следующего кадра телеметрии.

### Переходы по кнопке

Одна кнопка перегружена: её эффект зависит от текущего состояния.

| Из состояния | Действие |
|---|---|
| `IDLE` | → `SEEK_LOAD` (фиксирует опорную позицию для будущего возврата) |
| `SEEK_LOAD` или `HOLD_LOAD` | → `RETURN_HOME` |
| `ERROR` | запрос повторного homing → `IDLE` (восстановление без сброса по питанию) |
| `BOOT` / `HOMING` / `RETURN_HOME` | игнорируется |

Из `HOLD_LOAD` кнопка **всегда** ведёт домой. Повторный поиск к новой цели из удержания доступен только по сети (см. ниже) - одна кнопка не может
выразить «цель изменилась / не менялась», поэтому её поведение оставлено предсказуемым.

### Переходы по сети

Сетевые команды явные, их смысл не зависит от «первого/второго нажатия»:

| Команда | Из состояния | Действие |
|---|---|---|
| `seek` | `IDLE` | → `SEEK_LOAD` (фиксирует опорную позицию) |
| `seek` | `HOLD_LOAD` | → `SEEK_LOAD`: повторный поиск на лету к текущей цели без возврата домой |
| `home` | `SEEK_LOAD` / `HOLD_LOAD` | → `RETURN_HOME` |
| `home` | `ERROR` / `IDLE` | повторный homing (из `IDLE` - идемпотентный) |
| `stop` | `SEEK_LOAD` | → `HOLD_LOAD` (заморозка на месте, без возврата домой) |
| `calib_plus` / `calib_minus` | `IDLE` / `ERROR` | → `CALIBRATE`: медленное вращение в сторону роста / уменьшения угла |
| `stop` | `CALIBRATE` | остановка, текущий угол становится новым нулём (сохраняется в NVS) → `IDLE` |
| `home` | `CALIBRATE` | отмена: ноль не меняется, возврат к прежнему нулю |
| любая | неподходящее состояние | игнорируется с записью в лог |

Повторный поиск из `HOLD_LOAD` (`seek`) не перезахватывает опорную позицию `gHomeReferenceSteps`: это логический ноль, от которого считается предел
хода при возврате домой. Перезахват сместил бы точку отсчёта на нагруженную позицию и обошёл бы защиту предела хода.

Команда `home` из `IDLE` идемпотентна: если вал уже в домашнем окне, homing завершается за ноль шагов; если вал сместился в простое, он доводится
до дома. Кратко виден blip состояния `HOMING`.

### Калибровка нуля кулачков (CALIBRATE)

После замены кулачков их механический ноль не совпадает с сохранённым домашним углом. Калибровка задаёт ноль заново:

1. Команда `calib_plus` (в сторону поджатия платы) или `calib_minus` (от платы) переводит стенд в `CALIBRATE`. Вал вращается по одному шагу
   с интервалом `CALIB_STEP_INTERVAL_US` (около 18 °/с).
2. Когда кулачки встали в ноль, оператор шлёт `stop` (или нажимает кнопку на стенде). Вал останавливается, текущий абсолютный угол энкодера
   становится новым домашним углом, сохраняется в NVS (ключ `home`) и приходит событие `calib` с деталями `home=<новый> prev=<старый>`.
3. Все последующие homing и возвраты домой идут к новому углу. Он же приходит в телеметрии как `home_abs_deg`.

`HOME_ABSOLUTE_ANGLE_DEG` в `Config.h` теперь только значение по умолчанию для первого запуска.

Защиты (ноль при этом не меняется, стенд уходит в `IDLE`, событие `calib`):

| Условие | Деталь события |
|---|---|
| сделано `CALIB_MAX_TRAVEL_STEPS` шагов (2 оборота) без `stop` | `aborted_travel` |
| нагрузка выше `CALIB_MAX_LOAD_KG` и выше стартовой + `CALIB_LOAD_RISE_KG` | `aborted_load` |
| команда `home` | `cancelled` (и возврат к прежнему нулю) |

### Аварийные переходы в ERROR

Система уходит в `ERROR` при:

- неудаче стартового или повторного homing;
- отказе чтения энкодера подряд `ENCODER_READ_ERROR_LIMIT` раз;
- существенном рассогласовании энкодера **только во время `HOMING`** (в `SEEK`/`HOLD`/`RETURN_HOME` рассогласование - лишь диагностическое предупреждение);
- застревании, превышении хода или росте нагрузки при возврате домой.

**Достижение механической стенки в `SEEK_LOAD` авария НЕ вызывает** - это ожидаемый исход (объект зажат до предела), стенд паркуется на максимально
достижимой нагрузке (см. раздел 7). Выход из `ERROR` - по кнопке, по сетевой команде `home` или по физическому сбросу.

## 7. Логика поиска и удержания нагрузки

Это ядро прошивки. Вся управляющая логика построена вокруг одного принципа: **любое решение принимается только по нагрузке, измеренной в покое (мотор остановлен),
и по мгновенному сырому отсчёту, а не по запаздывающей медиане.**

### Почему измерение в покое, а не медиана

Медианный фильтр HX711 (окно 5, задержка 100+ мс) хорош для чистки одиночных выбросов в диагностике, но в управлении он вреден. В переходных процессах медиана
показывает старое значение: контроллер «видит» нагрузку там, где её уже нет, делает шаг, затем медиана догоняет реальность, он делает шаг обратно - и так бесконечно.
Это порождало автоколебания.

Решение - функция `measureSettledKg()`, вызываемая **только при остановленном моторе**. Она:

1. ждёт время успокоения (зависит от режима, см. ниже);
2. усредняет несколько **мгновенных** сырых отсчётов (не медиану), пропуская недопустимые (`raw <= 0`);
3. возвращает усреднённые килограммы и флаг «покоя»: сошлись ли отсчёты в пределах `SETTLED_MAX_SPREAD_KG`. Если нет - механизм ещё движется, замер не доверенный.

В покое мгновенный сырой отсчёт чистый (разброс порядка 0.002 кг), поэтому усреднение точнее медианы и, главное, не запаздывает.

### Три режима измерения

Время ожидания и число отсчётов масштабируются по близости к цели - чтобы не терять время там, где точность не нужна. **Число шагов мотора при этом не меняется**,
меняются только ожидание и число сэмплов.

| Режим | Когда | Ожидание | Отсчётов |
|---|---|---|---|
| `COARSE` | мёртвая зона: объект ещё не зажат, нагрузка около нуля | минимальное (8 мс) | 1 |
| `FAST` | нагрузка растёт, но до цели далеко | короткое (40 мс) | 2 |
| `PRECISE` | у цели, принимается решение о парковке | полное (400 мс) | 5 |

### Двухскоростной набор нагрузки

Импульс шага тоже двухскоростной:

- **дальняя фаза** - быстрый импульс `SEEK_STEP_INTERVAL_FAST_US`: нагрузка набирается быстро, случайный небольшой перелёт цели тут некритичен;
- **финальное центрирование** (в режиме `PRECISE`) - медленный высокомоментный импульс `SEEK_STEP_INTERVAL_US`: цель подбирается аккуратно.

### Алгоритм поиска (`parkIntoWindow`)

Функция работает тактами «шаг → стоп → успокоение → чистый замер в покое → решение»:

- шагает **к центру** окна: ниже цели - добавляет нагрузку, выше - сбрасывает;
- при попадании в окно и достижении цели - паркуется;
- если один шаг **перелетел через центр** (шаг грубее остатка до цели), выбирает сторону «до» или «после» шага, что ближе к центру, при необходимости откатывается на шаг и паркуется там, не гоняясь бесконечно за идеальным центром;
- при достижении стенки - паркуется на **максимально достигнутой** нагрузке (пике), а не на текущей.

Функция никогда не поднимает аварию: она либо паркуется (успех), либо прерывается при смене состояния (например, кнопка запросила возврат домой).

### Обнаружение стенки: четыре независимых детектора

«Стенка» - точка, где момента мотора не хватает провернуть вал дальше (объект больше не сжимается). Она не жёсткий предел и зависит в том числе от тока драйвера.
У стенки вал микро-дёргается около порога, а при срыве нагрузки откатывается назад. Один критерий физически не покрывает все режимы отказа, поэтому работают
четыре детектора. Все они паркуются на **пике** нагрузки (при срыве текущее значение уже упало, истинный максимум - это пик).

1. **Обрушение нагрузки** - нагрузка резко упала более чем на `WALL_LOAD_DROP_KG` ниже пика (объект сорвался/проскользнул) → немедленная парковка на пике.
2. **Плато нагрузки** - пик не растёт на `WALL_LOAD_GAIN_KG` за `WALL_NO_GAIN_STEPS` тактов, **при этом вал напрягается** (отставание от мотора превышает `WALL_PLATEAU_MIN_SLIP_DEG`). Проверка напряжения отделяет настоящую стенку от здорового медленного набора: при свободном нагружении вал вращается легко и плато не засчитывается. Прирост считается **накопительно** от опорной точки, а не «за один шаг».
3. **Проскальзывание вала** - вал отстал от мотора более чем на `WALL_SLIP_DEG` **за текущий поиск** (относительно базового рассогласования на входе). Измерение относительно базы нужно, чтобы повторный поиск из `HOLD_LOAD` со старым накопленным рассогласованием не парковался сразу.
4. **Угловой стопор** - вал не сделал движения **вперёд** `SEEK_STALL_LIMIT` тактов подряд. Считается именно «нет прогресса вперёд»: откат назад счётчик не сбрасывает.

### Мёртвая зона в начале поиска

В начале поиска есть большой мёртвый ход: вал проворачивается на много градусов, пока механизм выбирает люфт и доходит до объекта, а нагрузка всё это
время держится около нуля. Объект зажимается поздно.

Поэтому детекторы по нагрузке (обрушение, плато) **обязаны молчать**, пока `load < SEEK_ENGAGED_LOAD_KG`. Иначе «нагрузка не растёт» в мёртвой зоне
трактуется как стенка, и поиск ложно паркуется на нуле после пары шагов. В мёртвой зоне поиск ведут только угловой детектор и детектор
проскальзывания - там вал крутится свободно, и они не срабатывают. Как только объект зажат, опорная точка плато уже подтянута к текущей нагрузке,
счётчик обнулён, детектор стартует чисто.

### Удержание (HOLD_LOAD): жёсткая заморозка без подстройки

После парковки `HOLD_LOAD` - это **полная заморозка**. Мотор держит угол и не трогается, как бы ни менялось измеряемое значение. Единственный
выход - команда возврата домой.

Подстройка здесь пока что **сознательно запрещена**. Тензодатчик измеряет объект, зажатый между плитами, а угол вала задаёт силу зажатия. Значения
могут дрейфовать. Любой корректирующий шаг мотора изменил бы саму силу зажатия, то есть мог бы испортить измеряемую величину. Поэтому в итоге после
подтверждённой парковки позиция держится неизменной.

Прежняя логика подстройки оставлена в исходнике закомментированной как памятка на случай, если она окажется нужна.

## 8. Возврат в домашнюю позицию и стартовый homing

Остановка и захват нуля выполняются **по углу энкодера** (`HOME_ABSOLUTE_ANGLE_DEG`) с повторной верификацией. Выбор направления шага - ключевая
часть - делается **по углу и геометрии дуг**, а не по нагрузке и не по кратчайшему углу.

### Логический ноль

AS5600 даёт абсолютный угол только в пределах одного оборота и не знает истинного механического нуля всей системы без внешней опоры. Поэтому
реализован не абсолютный механический ноль, а **логический**: система доезжает к заранее зафиксированному абсолютному углу энкодера
(`HOME_ABSOLUTE_ANGLE_DEG = 106.08°`) и там захватывает ноль.

### Геометрия стенда асимметрична

Это причина, по которой направление выбирается по углу:

- **Нагрузочная дуга - короткая**: от дома вверх (рост угла) до стенки. Только здесь есть нагрузка.
- **Мёртвая зона - длинная**: от дома вниз, через границу 0/360 и по кругу обратно к стенке с другой стороны. Нагрузки нет.
- **Стенка** разделяет дуги; вал через неё не проходит.

### Правило выбора направления

Функция `homeStepDir()` вычисляет смещение от дома в положительную сторону, нормализованное в диапазон `[0, 360)`:

- смещение в `(0, LOAD_ARC_WIDTH_DEG]` → вал на **нагрузочной дуге** → шаг **вниз** к дому (сброс нагрузки, короткий путь);
- иначе (мёртвая зона) → шаг **вверх** к дому через 0/360, длинным путём, чтобы **не пересечь стенку**.

Направление пересчитывается на каждом шаге из текущего угла.

**Почему не кратчайший угол.** Геометрия асимметрична. Из мёртвой зоны кратчайший угол к дому может вести прямо в стенку. Правило по дугам
обходит стенку длинным путём.

**Почему не по нагрузке.** Тензодатчик ненадёжен для определения дуги: нагрузка идёт через механизм, и вал физически выше дома под нагрузкой
может показывать около нуля.
Классификация по нагрузке гнала бы вал в стенку.

`LOAD_ARC_WIDTH_DEG` - это ширина нагрузочной дуги, а не точный угол стенки (стенка плавает). Параметр берётся с запасом и подлежит подстройке.

### Две линии защиты от стенки

1. **Превентивная (основная)**: направление по дугам к стенке не ведёт.
2. **Реактивная**: при движении на сброс (вниз), если нагрузка растёт над базовым минимумом захода на `HOMING_LOAD_RISE_MARGIN_KG`, - это движение в стенку с другой стороны или заклинивание → стоп и `ERROR`. Сравнение именно с текущим минимумом, а не с абсолютным уровнем, поэтому нормальный сброс реальной нагрузки допустим.

### Защита от зависания возврата

Во время `RETURN_HOME` работает сторож отсутствия прогресса: если энкодер не показывает продвижения к дому дольше `RETURN_HOME_STALL_TIMEOUT_MS`,
возврат останавливается с аварией, а не крутится бесконечно. Есть и жёсткий предел общего хода `HOME_MAX_TRAVEL_STEPS`. Рассогласование
энкодера при возврате - только предупреждение (критично оно лишь в стартовом `HOMING`).

### Стартовый homing под нагрузкой безопасен

Поскольку направление выбирается по углу, автоматический homing при старте безопасен даже под нагрузкой: из-под нагрузки вал находится на
нагрузочной дуге и едет вниз к дому (сброс), а не вверх в стенку. Поэтому стартовый homing выполняется всегда, без ожидания разгрузки,
и идёт в `motorTask` - логи, WiFi и кнопка живы во время него.

## 9. Тензодатчик HX711: измерение, фильтрация, калибровка

### Перевод в килограммы

Килограммы считаются из сырого отсчёта вручную (драйверный `get_units` не используется):

```
кг = (raw - offset) / HX711_CALIBRATION_FACTOR
```

- `offset` - сырой отсчёт при нулевой нагрузке. Берётся не из константы `Config.h`, а из **оперативного** значения `gOffset` (см. раздел 10), поэтому перетарирование сразу влияет на расчёт.
- `HX711_CALIBRATION_FACTOR` - сколько единиц сырого отсчёта приходится на 1 кг.

Защитный фильтр отбрасывает результаты вне диапазона `[HX711_MIN_VALID_KG, HX711_MAX_VALID_KG]` и недопустимые сырые отсчёты (`raw <= 0`).

### Два канала: мгновенный и медианный

`LoadCellManager` за один цикл делает усреднённое чтение HX711, отбрасывает `raw <= 0` и ведёт два канала:

- **мгновенный сырой отсчёт** - используется управляющим путём в покое (см. раздел 7);
- **медианный** (скользящее окно 5) - диагностический канал, чистит одиночные выбросы. В управлении не используется намеренно: именно задержка медианы порождала автоколебания.

### Калибровка

Калибровка - чисто программная процедура, железо трогать не нужно. Нужно подобрать два числа в `Config.h`:

1. **Ноль (`HX711_OFFSET`)**. Пустой стенд, состояние `IDLE`, мотор стоит. Усреднить стабильный сырой отсчёт - это и есть ноль. Это значение служит лишь **умолчанием первой загрузки**: рабочий ноль живёт в `gOffset` и NVS и меняется перетарированием.
2. **Масштаб (`HX711_CALIBRATION_FACTOR`)**. Положить эталонный груз известной массы, снять сырой отсчёт в покое и посчитать:

   ```
   HX711_CALIBRATION_FACTOR = (raw_под_грузом - HX711_OFFSET) / масса_кг
   ```

Замер выполняется только при неподвижном моторе, с игнорированием `raw = 0` и одиночных выбросов.

### Прямое нагружение и нагружение через механизм

Масштаб откалиброван по грузу, приложенному **напрямую на ячейку** - это чистая калибровка самого датчика, и показанные килограммы
достоверны для такого нагружения. Во время рабочего поиска и удержания нагрузка приходит на датчик **через механизм** (плиты и зажатый объект).

Пока не подтверждено, совпадает ли сила зажатия объекта с показанием датчика при таком пути нагружения, - возможно, они отличаются.
Для текущей задачи (довести показание до целевого окна и удерживать) достаточно калибровки по прямому нагружению. Если же подтвердится
расхождение и понадобится измерять именно силу зажатия, масштаб стоит перекалибровать по реально ощущаемой нагрузке между плитами,
а не по прямому давлению на ячейку. Рекомендуемые способы:

- **Динамометр за подвижную плиту.** Приложить эталонное усилие динамометром к самой второй (подвижной) плите - за плиту, не за тензодатчик, - и по известному усилию пересчитать `HX711_CALIBRATION_FACTOR` рабочего датчика. Так усилие проходит через ту же цепочку передачи, что и при зажатии объекта.
- **Второй, эталонный тензодатчик между плитами.** Поставить между плитами второй тензодатчик, заранее откалиброванный прямым давлением на него. Он играет роль зажатого объекта и показывает реальную ощущаемую нагрузку; по его показанию подбирается `HX711_CALIBRATION_FACTOR` рабочего датчика.
- **Пересмотр расположения датчика.** Если расхождение окажется большим и стабильным, стоит пересмотреть само место тензодатчика в цепочке передачи усилия.

## 10. Перетарирование нуля на лету

Ноль тензодатчика **дрейфует** во времени (температура, усадка механики). В покое дома, без нагрузки, сырой отсчёт может уехать
от прошитого умолчания на тысячи единиц. Это десятки граммов ложной нагрузки. При этом мгновенный разброс в покое остаётся малым:
плавает не шум, а центр - классический дрейф нуля, датчик исправен.

### Дрейфует только ноль, масштаб - нет

Поскольку `кг = (raw - offset) / factor`, для устранения ошибки достаточно **пере-захватить ноль**. Эталонный груз пересчитывать
не нужно: `factor` считается из разности `raw - offset`, поэтому перетарирование автоматически сохраняет калибровку масштаба.

### Почему перетарирование, а не фильтр против дрейфа

Непрерывный авто-ноль здесь вреден. В `HOLD_LOAD` медленное изменение показания - это и есть измерение объекта (релаксация, ползучесть).
Фильтр не отличит «уехал ноль датчика» от «объект релаксирует» и молча испортит измеряемую величину. Поэтому дрейф давится не фильтром,
а **явной операторской операцией перетарирования в логическом нуле**.

### Как это работает

Оператор запускает перетарирование, когда стенд заведомо в нуле нагрузки. Новый ноль - это рантайм-значение `gOffset`, оно сохраняется
в NVS и переживает перезагрузку. Умолчание из `Config.h` остаётся лишь значением первой загрузки.

Запуск: `POST /v1/tare`, либо WebSocket-команда `tare`, либо кнопка в дашборде.

### Условия допуска (все обязательны)

Проверяются в `tryRetare()` по порядку, первая непройденная даёт причину отказа:

| Проверка | Токен отказа |
|---|---|
| состояние `IDLE` | `not_idle` |
| вал в логическом нуле (`|encoder_rel_deg| ≤ RETARE_MAX_REL_DEG`) | `not_home` |
| датчик выдал валидный отсчёт | `not_ready` |
| нагрузка около нуля (`|load_kg| ≤ RETARE_MAX_ABS_KG`) | `load_too_high` |
| захваченный ноль в пределах `[HX711_OFFSET_MIN, HX711_OFFSET_MAX]` | `offset_insane` |

Порог допустимой нагрузки (`RETARE_MAX_ABS_KG`, 50 г) выбран от величины дрейфа, а не от уровня шума: заведомо нагруженную ячейку затарировать нельзя.

### Детали реализации

- Замер усредняет `RETARE_SAMPLE_COUNT` свежих отсчётов **по медианно-фильтрованному** сырому значению - чтобы одиночный выброс рассинхронизации не попал в ноль и не был записан в NVS.
- Проверка вменяемости результата защищает сохранённый ноль от дикого отсчёта.
- Перетарирование выполняется на сетевой задаче и никогда не двигает мотор, поэтому безопасно относительно `motorTask`.
- Ноль сохраняется в NVS вместе с текущей тройкой конфигурации в едином блоке, поэтому запись нуля не затирает целевую нагрузку и наоборот.

### Обратная связь

Текущий ноль всегда виден в телеметрии полем `load_offset`, а готовность к перетарированию прямо сейчас - булевым `tare_ok`
(по нему дашборд включает и гасит кнопку). Результат приходит WebSocket-событиями: `ack` (принято/отклонено с причиной) и,
при успехе, `tare` с новым и прежним значением нуля.

## 11. Энкодер AS5600 и диагностика пропуска шагов

### Многооборотный учёт

AS5600 даёт абсолютный угол только в пределах одного оборота (4096 отсчётов). `EncoderTracker` накапливает многооборотную позицию,
разворачивая переходы через границу 0/4096: скачок больше половины оборота трактуется как переход границы и компенсируется.
Логический ноль - это зафиксированная опорная позиция, от которой считается относительный угол.

### Относительный угол до калибровки

До захвата логического нуля относительный угол показывает реальное отклонение от `HOME_ABSOLUTE_ANGLE_DEG` (кратчайшая разность до дома),
а не ноль. Это нужно, чтобы после перезагрузки в мёртвой зоне угол отражал действительное положение вала, а не мнимый ноль.
Только для отображения; детектор проскальзывания использует отдельный счётчик отсчётов.

### Диагностика пропуска шагов

Система непрерывно сравнивает две позиции:

- **ожидаемую** - по числу реально выданных на драйвер шагов (`0.45°` на шаг);
- **фактическую** - по энкодеру с многооборотным учётом.

Их разность - рассогласование `enc_err`. Если оно превышает `ENCODER_POSITION_ERROR_DEG`, выставляется флаг аварии энкодера. Это позволяет
диагностировать пропуск шагов, срыв механики, проблемы передачи момента и ошибки чтения.

### Разная критичность по состояниям

Рассогласование трактуется по-разному в зависимости от состояния:

- во время **`HOMING`** оно критично (homing ведётся по углу энкодера) - после `ENCODER_ERROR_LIMIT` срабатываний подряд система уходит в `ERROR`;
- во время **`SEEK_LOAD` / `HOLD_LOAD` / `RETURN_HOME`** это лишь диагностическое предупреждение с ограничением частоты (`WARN_THROTTLE_MS`); удержание стоит по нагрузке, а не по энкодеру, а застревание возврата ловит отдельный сторож прогресса.

Отдельно отслеживается отказ **чтения** энкодера: после `ENCODER_READ_ERROR_LIMIT` неудач подряд система уходит в `ERROR`.

## 12. Сетевой слой: REST и WebSocket

Микроконтроллер подключается к локальной WiFi-сети как station и **сам хостит** HTTP- и WebSocket-сервер. Дашборд - это клиент
(браузер в той же сети), который подключается к устройству. Устройство наружу ничего не пушит.

### Топология и обнаружение

- Хостнейм `1.esp32-s3` → адрес `1.esp32-s3.local` через mDNS. mDNS стартует лениво, как только поднялся WiFi.
- Если mDNS не резолвится на хосте (скорее всего, так и будет), используется сырой IP (он печатается в Serial-логе).
- Либо можно выделить IP по MAC-адресу и присвоить домен `1.esp32-s3` через панель администратора сети.
- WiFi-подключение не блокирует загрузку: стенд поднимается и работает даже без сети. При падении линка работает сторож переподключения.

### Принцип «команда = вторая кнопка»

Это главное решение сетевого слоя. Обработчик REST/WebSocket выполняется на отдельной задаче библиотеки AsyncTCP. Он
**не трогает автомат напрямую**, а лишь кладёт команду в очередь FreeRTOS (`sCmdQueue`). Основной `loop()` дренирует очередь
и применяет **ровно те же переходы**, что и физическая кнопка, через `onCommand()`.

Зачем:

- **единственный владелец переходов** - автомат двигает только `loop()`/`motorTask` на ядре 1, нет двух источников смены состояния с разных ядер, нет гонки;
- **безопасность движения** - команда не может дёрнуть мотор из неуместного состояния, действуют те же ограничения, что и для кнопки.

### Очередь событий

События (`state`, `park`, `wall`, `error`, `ack`, `tare`) эмитятся в том числе из `motorTask` (ядро 1). Прямая рассылка по WebSocket оттуда
брала бы мьютекс библиотеки и делала бы аллокацию - это внесло бы недетерминированную задержку в задачу управления мотором. Поэтому событие
кладётся в очередь `sEventQueue` неблокирующей функцией `queueEvent()` (копия JSON в фиксированный слот), а реальную рассылку делает `loop()`.
Очередь событий best-effort: при переполнении события теряются, телеметрия всё равно догонит состояние.

### REST API (v1)

База: `http://1.esp32-s3.local` или `http://<IP>`. Все ответы `/v1/*` несут заголовок CORS `Access-Control-Allow-Origin: *`.

| Метод и путь | Назначение |
|---|---|
| `GET /v1/health` | проба живости: `{"status":"ok","uptime_ms":...}` |
| `GET /v1/status` | полный снимок телеметрии (та же структура, что по WebSocket) |
| `POST /v1/command?cmd=seek\|home\|stop` | команда управления в очередь |
| `POST /v1/config?target=&min=&max=` | запись целевой нагрузки и границ окна (кг) |
| `POST /v1/tare` | перетарирование нуля тензодатчика |
| `OPTIONS /v1/*` | CORS preflight (204) |

Особенности:

- Команда передаётся **параметром** `cmd` (query или form-urlencoded), сырое тело запроса не читается. Ответы: `200` (поставлено в очередь), `400` (нет/неизвестная команда), `503` (очередь переполнена). Код `200` означает «поставлено в очередь», а не «выполнено»; фактический результат приходит WebSocket-событием `ack`.
- `POST /v1/config` валидируется на стороне прошивки: без `NaN`/`inf`, `min ≥ 0`, `min < max`, `min ≤ target ≤ max`. Жёсткого верхнего потолка нет - механическая стенка не фиксирована. Значения сохраняются в NVS. Если цель задана выше реальной стенки, это не ошибка валидации: поиск припаркуется на максимуме с событием `wall`.
- `POST /v1/tare` ставится в очередь команд и отдаёт `202`. Синхронно замер не выполняется (он занимает время и должен быть атомарен относительно автомата), поэтому результат приходит событиями `ack` и `tare`.

### WebSocket API

- URL: `ws://1.esp32-s3.local/ws` (или по IP). Лимит клиентов `NET_MAX_WS_CLIENTS`.
- **Клиент → устройство**: текстовый фрейм с именем команды (`seek`, `home`, `stop`, `tare`) - просто слово, без JSON. Регистр не важен, хвостовые пробелы и переводы строк обрезаются. Нераспознанное молча игнорируется.
- **Устройство → клиент**: три вида сообщений, все JSON - периодическая телеметрия, мгновенные события и подтверждения команд.

### Формат телеметрии

Транслируется всем клиентам каждые `NET_TELEMETRY_INTERVAL_MS` (около 5 Гц). Та же структура у `GET /v1/status`.

| Поле | Смысл |
|---|---|
| `state` | состояние автомата |
| `load_kg` | отфильтрованная нагрузка, кг |
| `target_kg`, `range_min_kg`, `range_max_kg` | целевая нагрузка и границы окна (рантайм) |
| `load_raw` | мгновенный сырой отсчёт HX711 |
| `load_ready` | `1`, если датчик выдал валидный отсчёт |
| `load_offset` | текущий оперативный ноль (сырые отсчёты) |
| `tare_ok` | `1`, если перетарирование прямо сейчас будет принято |
| `uptime_ms` | время с загрузки |
| `encoder_abs_deg` | абсолютный угол энкодера |
| `encoder_rel_deg` | угол относительно логического нуля |
| `encoder_fault` | `1` при рассогласовании/ошибке позиции |

Все поля берутся одним снимком под критическими секциями - они гарантированно из одного момента. Полей тока/напряжения/мощности здесь нет
и быть не может: это механический стенд, измеряется сила.

### Формат событий

При смене состояния, парковке, ошибке и на каждую команду шлётся отдельный event-фрейм: `{"event":..., "detail":..., "uptime_ms":...}`.

| Событие | Смысл `detail` |
|---|---|
| `state` | имя нового состояния |
| `park` | поиск припарковался в целевом окне (успех), достигнутая нагрузка |
| `wall` | поиск не дошёл до цели, припарковался на пике; сработавший детектор виден в Serial-логе |
| `error` | токен причины (`encoder_mismatch`, `return_home_stalled`, `home_travel_limit`, `homing_load_rise`, `boot_home_failed`, `rehome_failed`, `encoder_read_timeout`, `encoder_read_verify`) |
| `ack` | `<cmd>:ok` при приёме или `<cmd>:ignored_<состояние>` при отклонении; для `tare` - `tare:ok` или `tare:ignored_<причина>` |
| `tare` | при успешном перетарировании: `off=<новый> prev=<старый>` |

На парковку приходит ровно одно событие - `park` или `wall`, не оба.

### Настройки WiFi

`WIFI_SSID` и `WIFI_PASSWORD` задаются в `Config.h`. В прошивке прописаны учётные данные wifi сети - перед прошивкой их можно заменить
на другую приватную сеть. Значения `WIFI_SSID` и `WIFI_PASSWORD` меняются в `src/Config.h`, после чего плата перепрошивается. Если указать
placeholder SSID, сетевой слой молча не подключится, а при загрузке выводится громкое предупреждение в Serial.
ESP32 работает в диапазоне 2.4 ГГц; сеть только-5 ГГц не увидит.

### Сознательно не реализовано

Точки расширения на будущее, намеренно опущенные ради простоты:

- аутентификация WebSocket и HTTPS/TLS;
- хранение WiFi-кредов в NVS (смена сети - правка `Config.h` и перепрошивка);
- softAP-fallback при отсутствии роутера;
- отправка данных на внешний сервер (push наружу) - устройство работает только как сервер.

## 13. Хранение конфигурации в NVS

`ConfigStore` хранит в энергонезависимой памяти четыре значения единым блоком: целевую нагрузку, нижнюю и верхнюю границы окна и ноль тензодатчика. Единый блок означает одну запись во flash на сохранение.

- **Что переживает перезагрузку**: рабочее окно (`target`/`min`/`max`), заданное через `POST /v1/config`, и ноль (`offset`), заданный перетарированием. Умолчания из `Config.h` используются только при первой загрузке (пустая память).
- **При старте** конфигурация читается из NVS с откатом к умолчаниям. Если память пуста или блок повреждён, берутся умолчания и сразу записываются, чтобы значения были стабильны далее. Загрузка выполняется до старта задач, поэтому самый первый поиск использует заданное окно, а первое чтение датчика - сохранённый ноль.
- **Единый блок и запись** требуют осторожности: тот, кто меняет одну сущность (только окно или только ноль), обязан приложить текущее значение другой, иначе сохранение затрёт её. Оба пути записи в прошивке это соблюдают.
- **Валидация** при загрузке та же, что у `POST /v1/config`. Если тройка окна не проходит валидацию, берутся умолчания.

## 14. Диагностика через Serial

Основной канал наблюдения - Serial-монитор на скорости 115200. Каждые `SERIAL_REPORT_MS` печатается строка `[DIAG]`:

```
[DIAG] state=IDLE abs=104.59 rel=0.00 exp=0.00 load=0.000kg raw=122800 raw_f=122800 enc_err=0.00 fault=0 net=UP ip=1.esp32-s3.local ws=1
```

| Поле | Смысл |
|---|---|
| `state` | текущее состояние автомата |
| `abs` | абсолютный угол энкодера, град |
| `rel` | угол относительно логического нуля (около 0 в домашней точке) |
| `exp` | ожидаемое положение по выданным шагам |
| `load` | нагрузка в кг (диагностическое значение из медианного канала) |
| `raw` | мгновенный сырой отсчёт HX711 (выбросы видны здесь) |
| `raw_f` | медианно-фильтрованный сырой отсчёт |
| `enc_err` | рассогласование ожидаемой и фактической позиции |
| `fault` | флаг аварии энкодера |
| `net` | `UP`/`DOWN` - состояние WiFi |
| `ip` | адрес устройства (для дашборда, если mDNS не резолвится) |
| `ws` | число подключённых WebSocket-клиентов |

Норма: `abs` стабилен, `rel` близко к нулю после старта, `enc_err` близко к нулю, `fault=0`, мелкие плавающие значения нагрузки - обычный шум.

Повод разбираться: `fault=1`, большие скачки `abs` без движения механики, резкий рост `enc_err`, состояние `ERROR`, отсутствие лога старта после прошивки.

Помимо `[DIAG]` в лог идут переходы состояний (`[STATE]`), события кнопки (`[BUTTON]`), сетевые сообщения (`[NET]`) с суффиксом `(net)`
для переходов, инициированных сетью, и строки парковки `[PARK]` с указанием сработавшего детектора стенки.

## 15. Инструменты и окружение разработки

Раздел перечисляет инструменты, на которых велась разработка и прошивка. Составные части самого стенда здесь не описываются.

- **Ноутбук на Arch Linux** - рабочая машина сборки и прошивки.

- **Библиотеки** (тянутся PlatformIO автоматически по `platformio.ini`): `AS5600` (Rob Tillaart), `HX711` (Bogde), `AsyncTCP` и `ESPAsyncWebServer` (ESP32Async). `Wire` входит в ядро Arduino.
- **Прошивка по одному кабелю USB Type-C.** Плата запитывалась, прошивалась и отдавала Serial-лог через один и тот же кабель Type-C.
- **Serial через внешний USB-serial платы.** Лог читается не через native USB CDC, а через встроенный на плате USB-serial. Устройство появляется как `/dev/ttyACM0` (на Linux), скорость 115200; в мониторе `monitor_dtr = 0` и `monitor_rts = 0` (см. раздел 16).

Окружение сборки: платформа `espressif32`, framework `arduino`, плата `esp32-s3-devkitc-1`.

## 16. Сборка, прошивка и перенос на Windows

Сборка и прошивка ведутся через PlatformIO. Он тянет собственный toolchain (компилятор xtensa, Arduino-фреймворк, esptool), системный Python не модифицируется.

Окружение сборки: платформа `espressif32`, framework `arduino`, плата `esp32-s3-devkitc-1`.

```bash
pio run                 # сборка
pio run -t upload       # прошивка
pio device monitor -b 115200   # монитор
```

На первом прогоне PlatformIO скачает библиотеки. Устройство обычно доступно как `/dev/ttyACM0`.

### Особенность Serial на этой плате

Serial стабильно работает через внешний USB-serial интерфейс, а не через native USB CDC. Рабочая конфигурация (уже задана в `platformio.ini`):

- нет `ARDUINO_USB_CDC_ON_BOOT=1`;
- в мониторе `monitor_dtr = 0` и `monitor_rts = 0`.

Это особенность конкретной платы, не прошивки.

### Примечание про ошибки редактора

Сообщения вида `'Arduino.h' file not found` или `Unknown type name 'uint8_t'` от анализатора кода в IDE - это не ошибки сборки. Редактор
анализирует заголовки без путей toolchain ESP32. Лечится генерацией `compile_commands.json` через `pio run -t compiledb`; на прошивку не влияет.

### Перенос на Windows (Arduino IDE)

Проект переносится на Windows без правки исходников. Есть два пути.

**Путь A: PlatformIO в VS Code (проще всего).** На Windows установить VS Code и расширение PlatformIO IDE, открыть папку проекта как есть.
`platformio.ini`, набор библиотек и параметры платы переносятся без изменений; отличается только имя порта - вместо `/dev/ttyACM0` будет `COM<N>`.
Сборка и прошивка - теми же командами PlatformIO.

**Путь B: Arduino IDE.** Требует раскладки файлов под требования Arduino IDE:

1. Установить Arduino IDE.
2. Добавить поддержку плат ESP32: в настройках указать URL менеджера плат Espressif (`https://raw.githubusercontent.com/espressif/arduino-esp32/gh-pages/package_esp32_index.json`), затем в менеджере плат установить пакет `esp32` by Espressif Systems.
3. Выбрать плату `ESP32S3 Dev Module`.
4. Через менеджер библиотек установить все четыре библиотеки вручную: `AS5600` (Rob Tillaart), `HX711` (Bogde), `AsyncTCP` и `ESPAsyncWebServer` (ESP32Async). `Wire` уже входит в ядро.
5. **Раскладка скетча (ключевой момент).** Arduino IDE требует, чтобы главный `.ino` лежал в папке с тем же именем: `esp32s3_load_stand/esp32s3_load_stand.ino`. В этом проекте исходники лежат в `src/`, поэтому всё содержимое `src/` (главный `.ino` и все `.h`/`.cpp`) нужно разложить **плоско** в папку скетча рядом с `.ino`. Все внутренние `#include` локальные и без путей к подпапкам, поэтому после плоской раскладки правки исходников не требуются.
6. В настройках выбрать COM-порт платы, скорость монитора 115200. Serial-особенность платы (внешний USB-serial, без native CDC) сохраняется; в Arduino IDE отключается `USB CDC On Boot`.
7. Собрать и прошить штатной кнопкой.

Перед прошивкой в обоих путях в `src/Config.h` не забыть задать свою WiFi-сеть (см. раздел 12, «Настройки WiFi»).
